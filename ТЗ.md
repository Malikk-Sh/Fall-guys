Техническое задание: улучшение Wobble Rush 3D с акцентом на мультиплеер

Репозиторий: "Malikk-Sh/Fall-guys"

Цель проекта — превратить текущий браузерный прототип obstacle-racer в качественную мультиплеерную игру, у которой сетевой режим является основной визитной карточкой.

Не переписывай проект целиком без необходимости. Сначала изучи существующую архитектуру, затем внедряй изменения небольшими изолированными этапами. После каждого этапа проект должен запускаться, а существующие одиночный и сетевой режимы не должны ломаться.

Основной стек желательно сохранить:

- Three.js;
- JavaScript ES modules;
- Node.js;
- Express;
- WebSocket через библиотеку "ws";
- браузерный клиент без тяжёлого frontend-фреймворка.

---

1. Приоритеты

Используй следующие уровни приоритета:

- P0 — критично для рабочего мультиплеерного MVP;
- P1 — необходимо для качественной публичной версии;
- P2 — улучшает удержание и социальность;
- P3 — долгосрочное развитие.

Сначала полностью завершай P0, затем P1.

---

2. P0 — новая основа сетевой архитектуры

2.1. Разделить сетевой протокол на явные сообщения

Создай единое описание протокола, например:

shared/protocol.js

Определи константы или enum-подобный объект для сообщений:

HELLO
CREATE_ROOM
JOIN_ROOM
LEAVE_ROOM
ROOM_STATE
PLAYER_READY
HOST_CONFIGURE
START_COUNTDOWN
CLIENT_INPUT
SERVER_SNAPSHOT
PLAYER_CORRECTION
PLAYER_FINISHED
MATCH_RESULTS
REMATCH_VOTE
RETURN_TO_LOBBY
PING
PONG
ERROR

Для каждого сообщения зафиксируй:

- направление client → server или server → client;
- обязательные поля;
- допустимые типы;
- максимальный размер;
- возможные коды ошибок.

Не принимай произвольные объекты без проверки.

2.2. Добавить строгую валидацию входящих сообщений

На сервере создать централизованный валидатор.

Проверять:

- тип сообщения;
- размер JSON;
- наличие необходимых полей;
- тип каждого поля;
- диапазоны чисел;
- максимальную длину строк;
- допустимые состояния игрока;
- допустимую частоту сообщений.

При некорректном сообщении сервер должен:

1. проигнорировать действие;
2. отправить структурированную ошибку;
3. увеличить счётчик нарушений;
4. отключить клиента после нескольких серьёзных нарушений.

Формат ошибки:

{
type: "ERROR",
code: "INVALID_MESSAGE",
message: "Human-readable description",
recoverable: true
}

2.3. Перейти с отправки координат на отправку пользовательского ввода

Сейчас клиент не должен быть главным источником истины о позиции.

Вместо сообщения:

{
type: "state",
state: {
x,
y,
z,
vx,
vz
}
}

клиент должен отправлять input-команды:

{
type: "CLIENT_INPUT",
sequence: 184,
clientTick: 942,
moveX: 0.4,
moveZ: -0.9,
jumpPressed: false,
divePressed: true,
cameraYaw: 1.42
}

Сервер должен самостоятельно рассчитывать:

- ускорение;
- скорость;
- торможение;
- прыжок;
- состояние в воздухе;
- dive;
- гравитацию;
- импульсы;
- респаун;
- прохождение чекпоинтов;
- пересечение финиша.

Клиентская позиция может использоваться только для диагностики, но не как источник истины.

2.4. Вынести физические правила в общий модуль

Создать детерминированный модуль:

shared/simulation.js

Он должен использоваться и сервером, и клиентом.

Вынести туда:

- параметры движения;
- ускорение;
- максимальную скорость;
- drag;
- силу прыжка;
- гравитацию;
- длительность dive;
- cooldown dive;
- coyote time;
- jump buffering;
- обработку внешних импульсов;
- ограничения координат;
- модель состояния персонажа.

Не использовать внутри симуляции:

- "Date.now()";
- "performance.now()";
- случайные значения без seed;
- Three.js-объекты;
- DOM;
- браузерные API.

Функция должна принимать состояние, input и фиксированный timestep:

simulatePlayer(previousState, input, worldState, fixedDelta)

2.5. Добавить фиксированный серверный tick

Сервер должен обновлять матчи с фиксированной частотой.

Рекомендуемая начальная конфигурация:

simulation tick: 30 Hz
snapshot rate: 15–20 Hz
input send rate: 30 Hz
render rate: requestAnimationFrame

Добавить:

- номер серверного tick;
- sequence input;
- timestamp сервера;
- подтверждённый input sequence каждого игрока.

Не связывать физическую симуляцию с частотой поступления WebSocket-сообщений.

2.6. Реализовать client-side prediction

Локальный игрок должен реагировать на управление без ожидания сервера.

Клиент:

1. применяет input локально;
2. сохраняет input в очередь неподтверждённых команд;
3. отправляет input серверу;
4. получает авторитетное состояние;
5. удаляет подтверждённые команды;
6. повторно проигрывает оставшиеся input-команды.

Структура очереди:

pendingInputs = [
{
sequence,
tick,
input
}
]

2.7. Реализовать server reconciliation

Каждый серверный snapshot должен содержать:

{
playerId,
position,
velocity,
state,
checkpoint,
lastProcessedInput
}

После получения snapshot клиент:

- сравнивает серверную и локальную позиции;
- при небольшом расхождении плавно корректирует;
- при большом расхождении делает немедленный rollback;
- повторно применяет неподтверждённые input-команды.

Добавить настраиваемые пороги:

soft correction distance
hard correction distance
maximum reconciliation duration

2.8. Реализовать интерполяцию удалённых игроков

Не присваивать удалённому персонажу только последнее полученное состояние.

Хранить буфер снапшотов:

remoteSnapshots = [
{ serverTime, position, rotation, animationState },
...
]

Рендерить удалённых игроков с задержкой примерно 100–150 мс между двумя известными состояниями.

Добавить:

- линейную или Hermite-интерполяцию позиции;
- корректную интерполяцию угла через shortest path;
- ограниченную экстраполяцию при короткой потере пакетов;
- остановку экстраполяции после установленного таймаута;
- плавное восстановление после нового snapshot.

2.9. Синхронизировать препятствия

Все движущиеся препятствия должны иметь одинаковое состояние у сервера и клиентов.

Использовать:

- общий seed трассы;
- серверное время начала матча;
- детерминированную функцию состояния препятствия;
- стабильный ID каждого препятствия.

Пример:

getObstacleTransform(obstacleId, matchTime, courseSeed)

Сервер должен уметь вычислить положение препятствия в любой tick без доверия клиенту.

2.10. Серверная обработка столкновений

Добавить серверную упрощённую collision-модель для важных объектов:

- вращающиеся балки;
- толкатели;
- молоты;
- движущиеся платформы;
- бамперы;
- границы трассы;
- зоны падения;
- финиш;
- чекпоинты.

Не обязательно использовать полноценный физический движок на первом этапе. Допустимы аналитические collider-формы:

- AABB;
- sphere;
- capsule;
- oriented box;
- line/segment sweep;
- trigger volume.

Сервер должен рассчитывать финальный импульс от препятствия.

2.11. Исправить авторитетный финиш

Финиш должен подтверждаться серверной симуляцией автоматически.

Клиент не должен решать, что игрок финишировал, и отправлять доверенное сообщение "finish".

Сервер должен определить:

- игрок прошёл обязательные чекпоинты;
- игрок пересёк финишную плоскость;
- пересечение произошло в допустимой зоне;
- игрок не был уже финишировавшим;
- итоговое время основано на серверном tick.

После этого сервер отправляет:

{
type: "PLAYER_FINISHED",
playerId,
placement,
finishTime,
serverTick
}

2.12. Добавить защиту от спама

Ограничить отдельно:

- создание комнат;
- попытки входа;
- смену ready;
- изменение сложности;
- input-сообщения;
- ping;
- rematch;
- повторные респауны;
- сообщения после завершения матча.

Использовать token bucket или sliding window.

Добавить лимиты:

messages per second
burst allowance
maximum invalid messages
maximum room operations per minute

3. P0 — жизненный цикл комнаты и матча

3.1. Ввести явные состояния комнаты

Использовать state machine:

LOBBY
COUNTDOWN
RACING
RESULTS
CLOSING

Запрещать действия, не соответствующие текущему состоянию.

Примеры:

- нельзя менять сложность во время гонки;
- нельзя войти в обычном режиме после старта;
- нельзя отправлять ready в RESULTS;
- нельзя повторно запустить countdown;
- нельзя финишировать в LOBBY.

3.2. Добавить уникальный matchId

У каждой новой гонки должен быть уникальный:

roomId
matchId
courseSeed
matchStartTime

Все сетевые сообщения гонки должны содержать "matchId".

Это предотвратит применение запоздавшего snapshot от предыдущей гонки.

3.3. Улучшить старт гонки

Реализовать:

- готовность всех игроков;
- минимальное количество игроков, настраиваемое для production;
- серверный countdown;
- компенсацию рассинхронизации часов;
- блокировку input до стартового tick;
- старт всех игроков по одному server tick;
- отмену старта при критическом отключении хоста или сервера.

Показывать:

Waiting for players
All players ready
Starting in 3
Starting in 2
Starting in 1
GO

3.4. Поддержать вход зрителем после старта

Игрок, вошедший в уже начавшуюся комнату, должен иметь возможность:

- войти зрителем;
- увидеть текущих участников;
- увидеть позиции;
- увидеть таблицу лидеров;
- участвовать в следующем раунде.

Добавить отдельный статус:

PLAYER
SPECTATOR

3.5. Добавить переподключение

При временной потере соединения игрок не должен сразу исчезать из гонки.

Сервер должен выдавать reconnect token:

{
playerId,
roomCode,
reconnectToken,
expiresAt
}

При reconnect сервер восстанавливает:

- playerId;
- комнату;
- имя;
- цвет;
- checkpoint;
- позицию;
- статус финиша;
- место;
- неподтверждённый результат.

Рекомендуемое окно переподключения: 20–45 секунд.

Во время ожидания персонаж может:

- замереть;
- управляться простым bot takeover;
- перейти в безопасное состояние.

3.6. Исправить миграцию хоста

Миграция хоста должна быть детерминированной.

Выбирать нового хоста по критериям:

1. активное соединение;
2. не spectator;
3. дольше всех находится в комнате;
4. стабильный ping;
5. минимальный join sequence.

Отправлять отдельное событие:

{
type: "HOST_CHANGED",
previousHostId,
hostId
}

Показывать уведомление в UI.

3.7. Добавить корректное завершение матча

Матч заканчивается, когда:

- все активные игроки финишировали;
- истёк лимит времени после первого финиша;
- истёк абсолютный лимит раунда;
- все оставшиеся игроки отключились.

После первого финишировавшего запускать квалификационный таймер, например 30–60 секунд.

Оставшимся игрокам показывать:

30 seconds remaining
Qualified players: 4/8

3.8. Добавить DNF

Игроки, не успевшие завершить гонку, получают:

DNF

В итоговой таблице сортировать:

1. финишировавшие по времени;
2. DNF по максимальному checkpoint;
3. затем по прогрессу внутри сегмента.

3.9. Улучшить rematch

Добавить:

- количество голосов;
- список проголосовавших;
- таймер;
- правило принятия;
- возможность выбрать новую трассу;
- повторный старт без повторного ввода кода.

Варианты правила:

majority vote
all players
host decides

Для MVP использовать majority vote или host decides после таймера.

4. P0 — стабильность соединения

4.1. Реализовать автоматическое переподключение WebSocket

На клиенте добавить reconnect state machine:

DISCONNECTED
CONNECTING
CONNECTED
RECONNECTING
FAILED

Использовать exponential backoff:

0.5 s
1 s
2 s
4 s
8 s

Добавить небольшой random jitter.

Не создавать несколько одновременных WebSocket-подключений.

4.2. Не переводить гонку мгновенно в одиночный режим

При потере соединения в мультиплеерной гонке:

1. поставить сетевой режим на паузу или продолжить prediction;
2. показать reconnect overlay;
3. попытаться восстановить соединение;
4. вернуть игрока в гонку при успехе;
5. только после истечения reconnect timeout предложить одиночный режим.

Не менять режим автоматически без явного объяснения пользователю.

4.3. Улучшить heartbeat

Разделить:

- transport heartbeat WebSocket;
- игровой ping;
- timeout отсутствия input;
- timeout отсутствия snapshot.

Сервер должен различать:

socket disconnected
socket alive but player inactive
client tab suspended
network stalled

4.4. Добавить измерение качества сети

Рассчитывать:

- RTT;
- jitter;
- snapshot loss;
- input acknowledgement delay;
- количество reconciliation;
- максимальную correction distance.

Показывать пользователю простой индикатор:

Good
Unstable
Poor
Reconnecting

Числовой ping можно оставить в расширенной статистике.

8. P1 — взаимодействие игроков

8.1. Добавить физические столкновения между игроками

Сервер должен учитывать упрощённые capsule-collision между персонажами.

Требования:

- игроки не проходят полностью друг через друга;
- столкновения не создают экстремальных импульсов;
- клиент показывает столкновение плавно;
- сервер ограничивает penetration correction;
- при плохом ping поведение остаётся предсказуемым.

8.2. Добавить мягкое толкание

Толкание должно создавать весёлый хаос, но не позволять легко гриферить.

airborne multiplier

- угол;
- длительность;
- cooldown;

21. Порядок реализации

Этап 1 — протокол и room state machine

- создать "shared/protocol.js";
- добавить валидацию;
- добавить protocol version;
- ввести состояния комнаты;
- добавить "matchId";
- структурировать ошибки;
- сохранить совместимость текущего UI.

Критерий готовности: два клиента по-прежнему могут создать комнату, войти, нажать ready и начать матч.

Этап 2 — shared simulation

- вынести параметры движения;
- сделать фиксированный timestep;
- написать deterministic tests;
- перевести локальную физику на общий модуль.

Критерий готовности: одиночный режим ощущается почти так же, как до рефакторинга.

Этап 3 — input-based networking

- клиент отправляет input;
- сервер симулирует игроков;
- сервер отправляет snapshots;
- координаты клиента больше не являются источником истины.

Критерий готовности: два игрока корректно двигаются и видят друг друга.

Этап 4 — prediction и reconciliation

- добавить pending input queue;
- server acknowledgement;
- replay input;
- soft/hard correction;
- debug overlay.

Критерий готовности: управление остаётся отзывчивым при 150 мс RTT.

Этап 5 — remote interpolation

- snapshot buffer;
- interpolation delay;
- limited extrapolation;
- плавное восстановление.

Критерий готовности: удалённые игроки не дёргаются при нестабильном snapshot interval.

Этап 6 — препятствия и серверные столкновения

- детерминированное состояние препятствий;
- серверные collider;
- авторитетные импульсы;
- авторитетные checkpoint и finish.

Критерий готовности: клиент не может телепортироваться или подделать финиш.

Этап 7 — reconnect

- reconnect token;
- reconnect window;
- автоматические попытки;
- resync;
- UI overlay.

Критерий готовности: краткое отключение интернета не удаляет игрока из гонки.

Этап 8 — завершение матча

- qualification timer;
- DNF;
- results;
- rematch voting;
- spectator after start.

Критерий готовности: матч всегда корректно завершается даже при отключениях.

Этап 9 — UX лобби

- invite link;
- QR;
- улучшенный список игроков;
- состояние сети;
- host migration notification;
- ясные ошибки.

Этап 10 — тестирование и нагрузка

- Playwright;
- network simulation;
- load test;
- метрики;
- structured logging.

22. Definition of Done для мультиплеерного MVP

Мультиплеер можно считать готовым к публичному тесту, когда выполняются все условия:

- 16 игроков могут войти в одну комнату;
- все игроки начинают гонку синхронно;
- управление остаётся отзывчивым при RTT до 150 мс;
- удалённые игроки двигаются плавно;
- краткая потеря соединения допускает reconnect;
- отключение хоста не уничтожает комнату;
- сервер самостоятельно подтверждает checkpoint и finish;
- клиент не может назначить себе позицию или время;
- старые сообщения другой гонки игнорируются;
- есть qualification timer и DNF;
- rematch не требует нового входа;
- лобби поддерживает invite link;
- mobile UI работает в portrait и landscape;
- сервер переживает не менее 100 одновременных тестовых клиентов;
- нет необработанных исключений;
- все unit и integration tests проходят;
- E2E-тест двух браузеров проходит стабильно;
- health endpoint отражает реальное состояние сервера.

23. Формат работы над кодом

При выполнении задачи:

1. Сначала проанализируй текущие файлы.
2. Составь список файлов, которые потребуется изменить.
3. Не удаляй работающие механики без объяснения.
4. Выполняй работу этапами.
5. Для каждого этапа указывай:
   - что изменено;
   - какие файлы изменены;
   - какие риски остаются;
   - как проверить вручную;
   - какие тесты добавлены.
6. После каждого этапа запускай:
   - "npm test";
   - "npm run check".
7. Не скрывай ошибки тестов.
8. Не заменяй полноценную реализацию заглушками.
9. Не добавляй зависимости без обоснования.
