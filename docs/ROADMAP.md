# Wobble Rush 3D — чек-лист улучшений

Документ описывает полный план превращения текущего прототипа обстакл-рейсера в **кооперативную игру
на двух игроков** в духе _It Takes Two_, с попутной прокачкой графики, звука, камеры, сети,
производительности и стабильности.

Чек-лист рассчитан на передачу нейросети: каждый пункт самодостаточен — в нём есть цель, конкретные
файлы и критерий приёмки.

---

## Как пользоваться

Формат пункта:

```
- [ ] КОД-NN · Название                                   [приоритет]
  Зачем:        какую проблему решает
  Файлы:        что править или создавать
  Готово когда: проверяемый критерий приёмки
```

**Приоритеты**

| Метка | Смысл                                                                     |
| ----- | ------------------------------------------------------------------------- |
| `P0`  | Фундамент. Без него остальные пункты не сделать или сделать вдвое дороже. |
| `P1`  | Витрина. То, ради чего игрок останется и позовёт друга.                   |
| `P2`  | Полировка. Делать после P0 и P1.                                          |

**Разделы**

| Код       | Раздел                        |
| --------- | ----------------------------- |
| `TOOL`    | Инструменты и читаемость      |
| `ARCH`    | Архитектура и общий код       |

| `QA`      | Тесты, CI, деплой             |

## Состояние прототипа на старте

Проверено чтением всех 19 файлов исходников (~99 КБ).

**Что работает хорошо и это надо сохранить:**

- Комнаты, лобби, четырёхбуквенные коды, миграция хоста.
- Сервер владеет сидом трассы, сам выводит чекпоинты и валидирует финиш — гонку нельзя «срезать».
- Детерминированная процедурная генерация: 7 шаблонов сегментов из одного сида.
- Абстракция ввода: клавиатура и тач-джойстик за единым интерфейсом.
- Headless-стенд для тестов: `server/client-loader.mjs` умеет грузить клиентские ES-модули в Node,
  подменяя `/vendor/three.module.js` на npm-пакет. Редкая и очень полезная штука.
- Респонсивный CSS с учётом `env(safe-area-inset-*)`.

**Что сломано или отсутствует:**

| Проблема                                                                                                                                                                                                                                                                   | Где                                                         |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Звука нет вообще.** Ни одного упоминания Web Audio во всём репозитории                                                                                                                                                                                                   | —                                                           |
| **Часы не синхронизируются.** Сервер шлёт `serverTime` в `hello`, `pong` и каждом снапшоте — клиент не читает ни один. Фаза препятствий берётся из локального `Date.now()`, поэтому у игроков с расхождением системных часов вертушки бьют по тем, кто визуально увернулся | `client/net/NetworkManager.js`, `client/main.js` → `loop()` |
| **Нет буфера снапшотов.** Удалённый игрок лерпится к _последнему_ пакету, а не интерполируется между двумя → постоянное отставание и рывки                                                                                                                                 | `client/game/Player.js` → `applyRemote`                     |
| **Нет боковых коллизий.** Есть только приземление сверху; перила созданы с `collider:false` и являются декорацией. Столкновений игрок-игрок нет                                                                                                                            | `client/game/Course.js` → `surfaceAt`                       |
| **Тень не следует за игроком.** Ортографическая камера тени прибита к началу трассы — после второго сегмента теней нет                                                                                                                                                     | `client/main.js` → `createScene()`                          |
| **Каждый вызов `box()` создаёт новый материал** → сотни материалов и переключений шейдера на трассу                                                                                                                                                                        | `client/game/Course.js` → `material()`                      |
| Постобработки нет, геймпада нет, переподключения нет, линтера и типов нет                                                                                                                                                                                                  | —                                                           |

**Блокер номер ноль.** Код написан в предельно плотном стиле: в `styles.css` есть строка на 1867
символов, в `main.js` весь рендер-цикл — одна строка на 1513 символов. Номера строк бесполезны как
якоря для правок, а нейросеть такие строки надёжно редактировать не сможет. Поэтому `TOOL-01`
(переформатирование) обязателен первым — иначе весь остальной чек-лист неисполним.

## COOP · Кооперативный режим — главное

Основной принцип, заимствованный у _It Takes Two_: **асимметричные дополняющие способности плюс
преграды, которые физически невозможно пройти в одиночку.** Не «вдвоём быстрее», а «одному никак».

### Каркас

- [ ] **COOP-01 · Режим на двоих и роли** `P0`
      Зачем: базис всего раздела.
      Файлы: `server/coopRules.js`, `server/index.js`, `client/main.js`, `client/ui/UI.js`.
      Готово когда: комната ровно на 2 игроков; сервер назначает роли **ИСКРА** и **ГРУЗ**; роль видна в лобби и HUD.

- [ ] **COOP-02 · Асимметричные способности** `P0`
      **ИСКРА** — лёгкая: выше прыжок, есть планирование, луч-активатор, светит в тёмных зонах; сдувается ветром.
      **ГРУЗ** — тяжёлая: удар сверху, давит тяжёлые плиты, не сдувается ветром, может подбросить напарника; прыжок ниже.
      Файлы: `client/game/Player.js`, `client/game/abilities/`.
      Готово когда: ни одна секция кооп-главы не проходится одной ролью.

- [ ] **COOP-03 · Общая судьба** `P0`
      Зачем: без общей цены за ошибку кооп распадается на два параллельных забега.
      Файлы: `server/coopRules.js`.
      Готово когда: общий чекпоинт, общий таймер, финиш засчитывается только когда дошли оба.

- [ ] **COOP-04 · Оживление напарника** `P0`
      Зачем: превращает падение из личной неудачи в общую задачу.
      Файлы: `client/game/Player.js`, `server/coopRules.js`.
      Готово когда: упавший становится «пузырём» у последнего чекпоинта, напарник возвращает его касанием;
      авто-оживление через 12 секунд, чтобы не было тупика.

- [ ] **COOP-05 · Владение объектами** `P0`
      Зачем: без арбитража два клиента будут спорить за состояние одной платформы.
      Файлы: `server/coopRules.js`.
      Готово когда: у объекта есть владелец (первый коснувшийся), сервер разрешает конфликты по метке
      времени; импульсы игрок→игрок шлёт инициатор, сервер ограничивает модуль и ретранслирует.

### Механики

- [ ] **COOP-06 · Парные плиты** `P0`
      Двое встают на две плиты одновременно — открываются ворота. Обучающая механика первой главы.
      Готово когда: ворота не открываются в одиночку никаким способом.

- [ ] **COOP-07 · Катапульта** `P1`
      ИСКРА встаёт на конец рычага, ГРУЗ бьёт ударом сверху по другому концу — ИСКРА улетает через пропасть
      и открывает путь напарнику. Классический бит «по очереди».
      Готово когда: сила запуска зависит от высоты удара; ИСКРА стабильно долетает при правильном исполнении.

- [ ] **COOP-08 · Энергетический мост** `P1`
      ИСКРА держит луч на излучателе — пока держит, существует мост, по которому бежит ГРУЗ. Сама ИСКРА
      по своему мосту пройти не может.
      Готово когда: мост исчезает при уводе луча; ГРУЗ падает, если ИСКРА отвлеклась.

- [ ] **COOP-09 · Трос** `P1`
      Упругая связь между игроками с ограничением длины. Даёт: раскачку над пропастью (один держится,
      второй летит), вытягивание упавшего, рогатку для дальнего прыжка.
      Файлы: решается как ограничение расстояния на фиксированном шаге у обоих клиентов — позиции уже
      синхронизированы, отдельный авторитет не нужен.
      Готово когда: раскачка предсказуема, трос не «взрывается» при лаге.

- [ ] **COOP-10 · Синхро-ворота** `P2`
      Ворота открываются, только если оба пересекли линию в пределах 400 мс друг от друга.
      Готово когда: HUD показывает индикатор синхронности перед воротами.

- [ ] **COOP-11 · Бросок напарника** `P2`
      ГРУЗ поднимает ИСКРУ и бросает через препятствие; сила и направление задаются прицеливанием.
      Готово когда: траектория показывается пунктиром обоим игрокам.

- [ ] **COOP-12 · Зеркальные зоны** `P2`
      Управление одного отражается по горизонтали — партнёр должен вести словами.
      Готово когда: зона визуально обозначена, эффект понятен без объяснений.

- [ ] **COOP-13 · Общий транспорт** `P2`
      Платформа, где один рулит, второй разгоняет — движется только при обоих действиях.
      Готово когда: без второго игрока транспорт стоит.

- [x] **COOP-14 · Кооп-обучение** `P1` ✅
      Зачем: асимметричные механики без обучения отпугивают на первой минуте. Что ИСКРА прыгает
      выше, а ГРУЗ продавливает тяжёлые плиты, из геометрии не следует — это надо сказать, и
      сказать вовремя. Карточки главы на старте не хватало: она исчезает через пять секунд, задолго
      до задачи, про которую в ней написано.
      Файлы: `shared/coopChapters.js` (`lesson`, `resolveLessons`, `anchors` в разметке),
      `client/game/CoopCourse.js` (`activeLesson`), `client/main.js`, `client/ui/UI.js`,
      `client/index.html`, `client/styles.css`.
      Готово когда: урок — это данные рядом с той механикой, о которой он рассказывает. Точка
      появления берётся из разметки главы, а не пишется руками (иначе съедет при любой правке
      длин). У каждой роли свой текст: в один и тот же момент задачи у них разные. Подсказка
      держится, пока задача не решена, и не возвращается после — усвоенное не разучивается.
      Условие решения выводится из того же состояния, что и сами механики, поэтому обучение не
      требует ни одного дополнительного сетевого сообщения.
      Правило: каждая механика объясняется **ровно один раз**, в той главе, где впервые появляется —
      плиты и тяжёлые плиты в ch1, катапульта в ch2, луч с фиксатором в ch3, ветер в ch4,
      синхронные ворота в ch5. Тесты следят за обоими нарушениями: повтором и пропуском.

## Сверка с ТЗ.md

В репозитории лежит `ТЗ.md` — техническое задание, написанное под предыдущую версию проекта. Оно
ориентировано на **соревновательный** мультиплеер: матчмейкинг, регионы, боты, режимы Survival и
Score Hunt, турниры 16 → 10 → 6 → 1, DNF, таблицы лидеров. По решению заказчика соревновательная
ветка — отдельный режим, которым мы не занимаемся; из документа берутся только применимые к
кооперативу инженерные практики.

**Взято и сделано:** протокол с версией и кодами ошибок (2.1, 10.2, 10.3) · строгая валидация со
штрафными баллами (2.2, 13.2, 13.3) · machine состояний комнаты и `matchId` (3.1, 3.2) · буфер
снапшотов (2.8) · синхронизация препятствий через общее время (2.9) · переподключение по токену
(3.5, 4.1) · корректное завершение матча (3.7) · детерминированная миграция хоста (3.6) ·
индикатор качества связи (4.4) · одна сериализация на комнату (12.1) · backpressure (12.4) ·
остановка цикла неактивной комнаты (12.5) · лимиты ресурсов (12.6) · проверка источника (13.5) ·
заголовки безопасности (13.6) · разделение health-эндпоинтов и метрики (15.1–15.3).

**Взято, но ещё не сделано:** QR-код рядом со ссылкой (5.3) · настройки доступности (10.5) ·
нагрузочный тест (14.5) · E2E в Playwright (14.6).

**Сознательно не взято.** Пункты 2.3, 2.5–2.7, 2.10 требуют перенести всю физику на сервер:
клиент шлёт только ввод, сервер симулирует движение и считает столкновения. Это означало бы
портировать генерацию трассы в headless-представление без Three.js — самая дорогая работа во всём
документе. Её единственная цель — античит, а в кооперативе на двух друзей обман никому не вредит.
Поэтому из 2.4 взято главное — детерминированная общая симуляция, — а модель осталась прежней:
клиент считает себя, сервер проверяет; для кооп-объектов добавляются владение и проверяемые
события. Если соревновательный режим когда-нибудь понадобится, детерминированная симуляция —
ровно та основа, на которую он ляжет.

Не берутся вовсе: разделы 6 (матчмейкинг), 7.2–7.5 (соревновательные режимы и турниры),
3.4 и 3.8 (зрители и DNF), 18 (таблицы лидеров), 19 (масштабирование).

## Пересмотр после живой игры: роли убраны, препятствий больше

Заказчик прошёл главы и вынес приговор устройству режима, а не отдельным ошибкам. Изменения:

**Ролей больше нет.** Были две — ИСКРА и ГРУЗ, с разными прыжком, весом и способностями, и каждый
участок требовал определённой. Красиво на бумаге и плохо в игре: половину времени игрок упирался в
задачу, которую его роль решить не может, и ждал напарника. Любая ошибка в разметке при этом
превращалась в тупик — плита не той роли, пропасть шире прыжка тяжёлого, способность не у того.
Персонажи теперь одинаковые, а кооператив держится на присутствии: плиту надо КОМУ-ТО держать,
пока другой идёт. В одиночку по-прежнему никак, но кто держит и кто идёт — решают сами игроки и
меняются в любой момент. Планирование в воздухе и удар сверху стали доступны всем.

**Ворота открывает любая из плит.** Раньше требовались все сразу; теперь достаточно одной —
плит бывает несколько по разные стороны дорожки, и игроку не должно быть важно, до какой он добежал.

**Луч убран целиком** вместе с излучателями, площадками и сетевым сообщением наводки. Это была
самая непонятная механика игры и источник двух серьёзных ошибок подряд.

**Новых препятствий — четыре**, по трёхступенчатой шкале опасности из ТЗ:

| Препятствие        | Ступень     | Что делает                                                                   |
| ------------------ | ----------- | ---------------------------------------------------------------------------- |
| Конвейер           | мягкое      | тянет вдоль дорожки; сам не убивает, но сносит к тому, что убивает           |
| Вентилятор         | мягкое      | сдувает вбок; раньше это был «ветер» только для лёгкой роли, теперь для всех |
| Маятник            | жёсткое     | отбрасывает; рядом с краем этого достаточно                                  |
| Пресс              | смертельное | отправляет на чекпоинт, но в три такта: мигает → бьёт → поднимается          |
| Осыпающиеся плитки | мягкое      | пол исчезает под ногами и возвращается, чтобы второй не остался без пути     |

Правило трёх тактов для смертельных препятствий взято из ТЗ и соблюдается: внезапная смерть
читается как несправедливость, а не как ошибка игрока. У пресса есть фаза предупреждения с
миганием отметки на полу, у плиток — дрожание перед обрушением.

## Сетевые сбои жизненного цикла матча (по внешнему аудиту)

Аудит `Fallguysnetworkaudit.md` на коммите `10a1d37`. Два симптома, которые видел игрок, и один
дефект переподключения, который до симптома ещё не дорос.

- [x] **NET-11 · Хвостовой `state` после финиша** `P0` ✅
      Симптом: «когда второй игрок доходит до конца, происходит ошибка сервера» — каждый раз.
      Причина: клиент слал `finish`, сервер тут же переводил комнату в RESULTS, а следующий кадр
      того же клиента уже отправил `state`. Пакет приходил через миллисекунды, не проходил по
      таблице состояний и получал `WRONG_STATE` со штрафом за нарушение протокола.
      Как исправлено: клиент отправляет финиш атомарно — принудительное последнее состояние, сразу
      за ним `finish`, и после этого молчит о своей позиции до конца матча. Сервер, со своей
      стороны, молча гасит хвост забега в RESULTS вместо начисления нарушения.
      Файлы: `client/net/NetworkManager.js` → `finish`/`sendState`, `client/main.js` → `localFinish`,
      `server/index.js` → `MATCH_TRAILING_TYPES`.

- [x] **NET-12 · Финиш проверялся по устаревшей позиции** `P0` ✅
      Позиция уходила на сервер раз в 66 мс, а `finish` — из физического шага. Сервер видел
      позицию до черты, отказывал обычной коррекцией, клиент считал себя финишировавшим и второй
      раз не просил — вечное «Подтверждаем результат…».
      Как исправлено: принудительное состояние перед финишем (см. выше) плюс отдельный ответ
      `finishRejected`, по которому клиент возвращается в игру и может добежать ещё раз.

- [x] **NET-13 · Окно голосования не держалось** `P0` ✅
      Симптом: «почти невозможно, чтобы держалось окно голосования нового забега».
      Причин было две. На сервере голос хоста единолично распускал комнату в лобби. На клиенте
      состояние комнаты приходит одним типом сообщения в любом состоянии, а обработчик этого не
      различал и на каждое обновление открывал лобби — то есть даже чужой голос закрывал карточку
      результатов.
      Как исправлено: реванш и возврат в лобби — единогласные решения и только в RESULTS; клиент
      различает состояние комнаты и на RESULTS обновляет только счётчик голосов.

- [x] **NET-14 · После `resume` клиент хранил чужой id и токен** `P0` ✅
      Сервер выдаёт `hello` каждому новому сокету, включая тот, которым мы возвращаемся в старую
      комнату. Клиент принимал эту временную личность сразу: сервер считал игрока прежним, клиент
      себя — новым. Он переставал узнавать себя в снапшотах, а следующая попытка восстановления
      уходила с уже удалённым токеном.
      Как исправлено: `hello` во время восстановления считается предварительным, `resumed` приносит

      комнате и отдаются заново.

- [x] **NET-20 · Лимиты по адресу за обратным прокси** `P1` ✅
      За Nginx `remoteAddress` — адрес прокси, один на всех, и лимиты делились между всеми игроками.
      `TRUST_PROXY=1` включает разбор `X-Forwarded-For`; конфигурация Nginx описана в README.
      Там же — почему клиенту и `shared/` нельзя добавлять кэш на прокси.

## Ошибки, найденные и исправленные по ходу работы

Их не было в исходном плане — всплыли при чтении и правке кода. Перечислены, чтобы вы понимали,
что именно изменилось в поведении игры.

- **Прозрачность частиц применялась ко всем сразу.** `Effects` кэшировал материалы по цвету, а
  затухание выставлялось через `material.opacity` — то есть на общий для всех частиц объект. Вместо
  плавного угасания частицы одного цвета мигали вместе, принимая прозрачность той, что обновилась
  последней. Заменено на набор материалов по ступеням прозрачности.
- **Выталкивание из препятствий уходило в никуда.** После разделения позиции физики и позиции
  отрисовки метод `Course.interact` продолжал бы менять позицию отрисовки, которая пересчитывается
  заново каждый кадр. Любое выталкивание из бампера или вертушки немедленно затиралось бы. Исправлено
  до того, как попало в игру.
- **Постобработка отключала тональную компрессию.** `OutputPass` берёт кривую из
  `renderer.toneMapping`; выставленный там `NoToneMapping` означал, что компрессия не выполняется
  нигде, и картинка была полностью пересвечена.
- **Порог свечения задавался как будто в диапазоне 0..1.** Сцена освещена очень ярко, и в линейном
  HDR почти всё выше единицы, поэтому в свечение попадала вся картинка разом. Порог поднят до 2.2, а
  эмиссия тех объектов, которые действительно должны светиться, поднята им навстречу.
- **Мёртвый код.** Сообщение `checkpoint` отправлялось клиентом, но обработчика на сервере не имело;
  `bindNetworkEvents()` был пустой заглушкой; `fallGrace` в настройках сложности не читался нигде;
  параметр `side` в `addRail` не использовался.
- **404 на `/favicon.ico`.** Добавлен встроенный SVG-фавикон как data-URI, без файла-ассета.
- **Оценка часов была систематически смещена на время пути пакета.** Приветственное сообщение
  сервера клалось в набор замеров как пара «сейчас, серверное время», то есть с нулевым RTT. Такой
  замер навсегда выигрывал выбор минимума, и ни один настоящий ping уже не мог уточнить оценку. На
  локальном сервере смещение показывало −51 мс вместо −1 мс; ровно на эту величину расходилась фаза
  препятствий у игроков. Теперь начальная оценка живёт отдельно и заменяется первым же реальным
  замером.
- **Индикатор качества связи навсегда залипал в «плохую».** Пропуски снапшотов считались
  накопительным счётчиком без сброса: за долгую сессию он неизбежно дорастал до любого порога.
  Заменён на подсчёт за последние десять секунд.
- **Строгая CSP заблокировала бы собственную загрузку игры.** Import map обязан быть встроенным в
  HTML, а `script-src 'self'` такие скрипты запрещает — игра не стартовала вообще. Сервер считает
  хеш содержимого карты при запуске, поэтому политика остаётся строгой и не ломается при её правке.
- **Тип `START_MATCH` был объявлен без схемы.** Валидатор считал его неизвестным и молча отклонял
  запуск забега. Добавлен тест, проверяющий, что у каждого клиентского сообщения есть и схема, и
  ограничение частоты.
- **Главы были непроходимы, а все тесты — зелёными.** Заказчик попробовал пройти кооп и не смог
  ни одного препятствия. Причина не в одной ошибке, а в том, ЧТО проверялось: тесты спрашивали
  «работает ли механизм», а надо было спрашивать «может ли пара пройти дальше». Ниже — всё, что
  нашлось, когда вопрос поменяли и написали ботов, которые просто играют.
- **Ворота с парными плитами не имели решения.** Пролёт держался, пока обе плиты нажаты, а нажать
  их можно только стоя на них. Сойти, чтобы перейти, значило убрать пролёт — из-под себя или из-под
  напарника. Пролёт при этом честно выдвигался, и тест это подтверждал; он просто ни для кого не был
  проходим. Ворота переделаны на трёхтактную схему, как у светового моста: один держит плиту →
  второй переходит → второй встаёт на фиксатор за пролётом → первый переходит следом.
- **На каждом стыке отрезков пола была щель.** Опора считалась с отступом ВНУТРЬ на 0.12 от каждого
  края платформы, а отрезки трассы кладутся вплотную — значит между соседями оставалось 0.24, где
  пола не было ни у одного. Игрок проваливался посреди ровного пола, в месте, где визуально нет
  ничего. Глазами такое не находится: щель уже персонажа, и падение случается, только если шаг
  физики придётся ровно на неё. Знак отступа теперь противоположный — край опоры чуть шире
  геометрии, стыки заведомо перекрываются, а прыжок с самого края стал прощающим.
- **Луч не наводился вблизи.** Направление на излучатель бралось в трёх измерениях, а взгляд по
  построению горизонтален — камера даёт только рыскание. Излучатель стоит на столбе выше игрока,
  поэтому чем ближе подходишь, тем круче вверх смотрит вектор на цель и тем меньше его скалярное
  произведение со взглядом. Навести можно было только издалека, с шести единиц и ближе — уже нет,
  а обучение как раз велит подняться на площадку и встать рядом. Игрок делал всё правильно, держал
  кнопку, и ничего не происходило. Сравнение переведено в горизонтальную плоскость.
- **Катапульты не добрасывали.** Сила подбиралась на глаз, а дальность полёта складывается из
  импульса, гравитации, планирования и управления в воздухе — по числам в разметке её не видно.
  ИСКРА улетала в пропасть и возвращалась к чекпоинту. Наклон броска стал свойством катапульты,
  сила подобрана измерением, а тест проверяет, что каждая катапульта перебрасывает через свою
  пропасть.
- **После катапульт стояли голые пропасти.** ИСКРУ через них перебрасывало, а ГРУЗУ перебраться было
  нечем: механизма на той стороне не существовало. Тупик того же класса, что и ворота без фиксатора,
  только с другой стороны. Все такие пропасти перекрыты воротами с плитой за ними — той самой, на
  которую встаёт перелетевшая ИСКРА.
- **Дубль идентификатора плиты.** Допущен при правке глав: вторая плита затирала первую в карте
  объектов, и механика, ссылавшаяся на первую, начинала управляться другой плитой в другом конце
  главы. Добавлена проверка уникальности.

- **Синхронные ворота были непроходимы вовсе.** Окно синхронности 800 мс, а перейти надо
  четырнадцать единиц — почти две секунды бега. Пролёт исчезал прямо из-под идущих, примерно на
  середине. Пара делала всё правильно, попадала в окно, ступала на появившийся пролёт и падала.
  Задача этих ворот — заставить действовать одновременно, а не обогнать таймер, который обогнать
  нельзя. Условие теперь защёлкивается: синхронность доказана в момент попадания в окно, дальше
  пролёт просто стоит.
- **ГРУЗ не мог перепрыгнуть «узкую» пропасть.** В первой главе стояла пропасть в 5 единиц с
  подсказкой «перепрыгните сами». Измерено: ИСКРА берёт 6.2 обычным прыжком и 7.7 с планированием,
  а ГРУЗ — 4.7, причём рывка у него в кооперативе нет вообще: кнопка занята ударом сверху, а
  нажатие на земле просто съедается. То есть 4.7 — его потолок. Пропасть была шире, и ГРУЗ
  застревал там навсегда. Ширина таких пропастей теперь считается от измеренной дальности слабой
  роли с запасом в четверть, и тест меряет прыжок сам, а не верит константе в комментарии.
- **Мой собственный тест засчитывал падение как успех.** Успехом перехода считалось «координата
  стала меньше отметки». За время падения сквозь исчезнувший пролёт координата тоже проскакивает
  нужную отметку — и тест радостно рапортовал о прохождении, пока оба летели в пропасть. Именно
  так синхронные ворота и прошли проверку. Теперь успех — это «стоит на той стороне НА НОГАХ».
- **Тест «от начала до конца» до конца не доходил.** Он проверял все кооперативные преграды и
  останавливался на последней, а участок до финишной черты — качели, узкие пропасти, просто
  длинный пол — оставался непроверенным. То же расхождение между названием и содержанием, из-за
  которого главы и оказались непроходимыми. Именно оно и скрывало две ошибки выше.

- **Усвоенная подсказка возвращалась.** Найдено при живой проверке в двух браузерах. Условие урока
  проверялось как текущее состояние: пролёт выдвинут, пока обе плиты нажаты. Пара решала задачу,
  переходила по пролёту, сходила с плит — пролёт убирался, состояние возвращалось в исходное, и
  игрокам, уже стоящим на той стороне, снова показывали «встаньте на плиты». Условие описывает
  момент, когда стало понятно, а не состояние, которое надо удерживать, — усвоенные уроки теперь
  запоминаются.
- **Звук пролёта играл бы из чужого места.** Выдвижение пролёта озвучено арпеджио из трёх нот, а
  позиция для него бралась из общего временного вектора трассы. Первая нота звучит сразу, остальные
  — через десятки миллисекунд, и к этому моменту в векторе уже лежат координаты совсем другого
  объекта: тот же вектор каждый кадр переиспользуют наводка луча и отрисовка лучей. Координаты
  теперь копируются в момент вызова.
