# Косметика и шкаф — Content & Customization 2.0

Документ описывает косметическую подсистему Wobble Rush: канонический каталог, слоты, редкости,
коллекции, модель выдачи, границы владения, устройство рендерера и правила производительности.
Он же отвечает на главный практический вопрос — **как добавить новый предмет**.

Источник истины — код. Если этот документ разошёлся с `shared/cosmetics.js`, прав код.

---

## 1. Канонический каталог

```text
shared/cosmetics.js          собирает каталог, нормализует записи, публичные loadout
shared/cosmeticContent.js    данные шестидесяти предметов Content & Customization 2.0
shared/cosmeticMeta.js       редкости, коллекции, слоты, типы выдачи
shared/cosmeticUnlocks.js    декларативный резолвер условий выдачи
shared/cosmeticValidation.js проверка каталога (используется тестами)
```

Каталог **один** и общий для браузера и сервера. Отдельного «серверного каталога», который надо
поддерживать вручную, нет и заводить его нельзя: расхождение двух списков ID проявляется как
«предмет надет, но не виден у других», и найти причину постфактум крайне тяжело.

Разбиение на файлы чисто механическое: `COSMETIC_CATALOG` по-прежнему собирается в одном месте, а
`COSMETIC_BY_ID` строится из него.

```js
import { COSMETIC_CATALOG, COSMETIC_BY_ID, publicCosmeticLoadout } from '/shared/cosmetics.js';
```

### Что нельзя менять

ID унаследованных предметов — `classic`, `sky-hero`, `clear-visor`, `rescue-antenna`, `neon-visor`,
`party-antenna`, `sunrise-trail`, `campaign-finish`, `racer-body`, `champion-visor`,
`veteran-antenna`, `podium-trail`, `streak-trail`, `champion-finish` — нельзя удалять,
переименовывать, переносить в другой слот или переосмыслять. Они лежат в базах игроков и в
сохранённых образах.

Старые поля (`colors`, `color`, `glyph`, `achievement`, `localGoal`, `rewardable`) продолжают
читаться. У новых предметов вместо них `render` и `unlock`, но у старых остались оба набора.

## 2. Слоты

| Ключ      | Метка в интерфейсе | Что туда надевают                           |
| --------- | ------------------ | ------------------------------------------- |
| `body`    | ТЕЛО               | корпус персонажа, полноценный skin          |
| `visor`   | ЛИЦО               | визоры, очки, маски, декоративные глаза     |
| `antenna` | ГОЛОВА             | антенны, короны, шляпы, уши, рога           |
| `back`    | СПИНА              | рюкзаки, баллоны, сундуки, бочки            |
| `trail`   | СЛЕД               | след движения                               |
| `finish`  | ПОБЕДА             | победная презентация                        |
| `emote`   | ЭМОЦИИ             | эмоции (отдельный loadout на четыре ячейки) |

Внутренний ключ `antenna` сохранён ради совместимости с колонкой в базе и сохранёнными образами,
но смысл слота шире названия. Показывать игроку слово «антенна» было бы прямой ложью, поэтому
метка отвязана от ключа и живёт в `SLOT_META`.

`body` обязателен: снять его нельзя, и ровно один предмет в каталоге выдаётся по умолчанию
(`classic`). Это проверяется валидатором.

`emote` **не входит** в `COSMETIC_SLOTS`: у эмоций не один слот, а четыре позиции, и смешивать их
с носимыми означало бы либо ломать `equip`, либо заводить четыре псевдослота.

## 3. Редкости

```text
common · rare · epic · legendary · mythic · prestige
```

Метаданные — в `RARITY_META`. Каждая ступень несёт **словесную метку, значок и короткую метку**
помимо цвета: требование доступности — редкость должна читаться без цветового зрения.

- **Common** — простая форма или цвет.
- **Rare** — заметная форма.
- **Epic** — форма плюс лёгкая анимация или эффект.
- **Legendary** — сложная презентация.
- **Mythic** — динамический материал и сильная визуальная идентичность.
- **Prestige** — награда за тяжёлое достижение. Не продаётся и не выдаётся за рекламу; это
  свойство класса, а не отдельного предмета, и валидатор его проверяет.

Редкость **не влияет ни на один игровой показатель**.

## 4. Коллекции

Четыре тематические коллекции по пятнадцать предметов:

```text
space-trouble  15   КОСМИЧЕСКИЕ НЕПРИЯТНОСТИ
food-fight     15   ЕДА В БОЮ
neon-arcade    15   НЕОНОВЫЙ АРКАД
pirate-panic   15   ПИРАТСКАЯ ПАНИКА
```

Реестр — `COLLECTION_META`. Прогресс считает `collectionProgress(ownedIds)`: собранное, всего,
процент, признак полноты и список мифических предметов коллекции.

Собранная коллекция даёт значок и ничего больше. Игрового бонуса за неё нет намеренно.

## 5. Модель выдачи

Условие живёт в самом предмете:

```js
unlock: { type: 'stat', path: 'race.finishes', gte: 10 }
unlock: { type: 'achievement', id: 'race-win' }
unlock: { type: 'daily', streak: 7 }
unlock: { type: 'rewarded' }   // event | shop | pass — каталог готов, механики нет
```

Читает их **один** резолвер — `shared/cosmeticUnlocks.js`. Шестидесяти веток `if (item.id === ...)`
нет ни на клиенте, ни на сервере, и появляться им нельзя.

### Пути статистики

`cosmeticStats(progress, profile)` сводит серверный прогресс и локальный профиль к плоской форме:

```text
race.finishes   race.wins      race.podiums
coop.matches    coop.chapters  coop.revives   coop.flawless   coop.ch10Runs
daily.bestStreak
```

### Кто что решает

| Тип                                 | Кто выдаёт                                          |
| ----------------------------------- | --------------------------------------------------- |
| `default`, `achievement`, `stat`    | Только сервер (`InventoryService.syncEntitlements`) |
| `daily`                             | Клиент — серия никогда не была серверной            |
| `rewarded`, `event`, `shop`, `pass` | Никто. Каталог готов, источника выдачи нет          |
| `admin`                             | Ручная выдача                                       |

**Новый контент не выдаётся клиентом.** Без серверного инвентаря предметы с `expansion:
'customization-2'` остаются закрытыми, даже если локальная статистика формально подходит: посчитать
их самому означало бы client-authoritative ownership для шестидесяти предметов сразу. Единственное
исключение — `daily`, которую сервер не считает вовсе.

Унаследованные награды продолжают открываться локально ровно как раньше: у трёх кооперативных есть
`unlock.localStat` — локальный фолбэк, без которого гость терял бы уже полученное.

## 6. Владение и equip

```text
клиент просит equip ID
  → сервер проверяет слот
  → сервер проверяет ownership
  → сервер сохраняет
  → сервер возвращает канонический loadout
```

Клиент **не может**:

- прислать собственный цвет или материал — по сети едут только ID;
- объявить неизвестный ID — он не пройдёт `publicCosmeticLoadout`;
- надеть предмет в чужой слот;
- надеть невыданный предмет;
- подменить косметику другого игрока;
- снять `body`.

`back` проходит ровно те же проверки, что и остальные слоты: он добавлен в `COSMETIC_SLOTS`, и
подготовленные запросы `InventoryService` строятся по этому списку, а не перечислением.

Публичный loadout содержит только канонические ID:

```js
{ body: 'space-astronaut', visor: 'space-nebula-visor', antenna: 'space-star-crown',
  back: 'space-oxygen-pack', trail: 'space-stardust-trail', finish: 'space-portal-finish' }
```

Старый payload без `back` нормализуется в `null`, а не отбрасывается.

### Персистентность

```text
account_loadout              +колонка back (nullable, миграция 017)
account_emote_loadout        account_id, position 0..3, cosmetic_id, updated_at
```

Emote loadout хранится строками, а не JSON-полем: массив одной строкой перестал бы быть данными
базы и стал бы непроверяемым текстом от клиента. Позиция — часть первичного ключа, поэтому
дубликат в одной ячейке невозможен по схеме.

Старый аккаунт после миграции: все слоты сохраняются, `back` становится `NULL`, emote loadout —
пустым, владение и достижения не трогаются.

## 7. Эмоции по сети

```js
// клиент → сервер
{ type: 'emote', emoteId: 'food-chefs-kiss' }
```

Единственное поле. Ни длительности, ни поз, ни настроек анимации: всё это чужой клиент берёт из
общего каталога сам. Иначе отправитель диктовал бы, что рисовать в чужом рендере.

Сервер проверяет по порядку:

1. отправитель — участник комнаты (до обработчика доходят только `room` + `player`);
2. у отправителя есть аккаунт (у гостя нет ни владения, ни выбора);
3. ID канонический и его слот — `emote`;
4. предмет принадлежит аккаунту;
5. предмет выбран в текущем emote loadout — проверяется **на каждое сообщение**, потому что выбор
   меняется в шкафу между двумя нажатиями;
6. частота в пределах `RATE_LIMITS` (≈2/сек, burst 3);
7. рассылается санитизированное событие `{ type, id, emoteId, at }`.

Эмоция не меняет authoritative state: ни позиции, ни скорости, ни чекпоинта. В обработчике
`server/index.js` нет ни одной строки, которая трогала бы игрока.

Локально эмоция прерывается прыжком, подкатом и сменой состояния забега.

## 8. Рендерер

```text
client/game/cosmetics/
  CosmeticResources.js    общие кэши геометрий, материалов и текстур
  AccessoryFactory.js     реестр render kinds → сборка THREE.Group
  AccessoryAnimator.js    вторичное движение
  TrailSystem.js          следы: пул частиц + GhostTrail
  FinishEffectSystem.js   победная презентация
  EmoteSystem.js          позы эмоций
  CosmeticRenderer.js     оркестратор одного персонажа
  CosmeticPreview.js      превью шкафа
```

Принцип: **данные каталога → render kind → переиспользуемая фабрика**. `Character.js` не содержит
ветвления по ID предметов; он даёт риг и якоря, а что куда надевать — решает `CosmeticRenderer` по
данным.

### Точки крепления

```text
faceAnchor   headAnchor   backAnchor   bodyAnchor   trailAnchor   fxAnchor
```

Это пустые `THREE.Group` внутри `visual`. Опираться на `visual.children[n]` в новой системе нельзя:
индексы ломаются от любой правки порядка добавления и ломаются молча.

Унаследованные `face-plate` и `head-antenna` не строят собственной геометрии — они перекрашивают
базовые детали персонажа. Так старые предметы выглядят ровно как до этой системы.

### Render kinds

Список объявлен в `shared/cosmeticValidation.js` (`RENDER_KINDS`) — это часть контракта данных.
Реализация — в `AccessoryFactory.js`. Тест проверяет, что реестр покрывает список ровно, без
лишнего и без недостающего.

## 9. Производительность

Это мобильный веб, и бюджет считается на **полную комнату из шестнадцати персонажей**, а не на
одного локального.

Запрещено:

- `new Geometry` / `new Material` в кадре;
- неконтролируемые клоны персонажа;
- неограниченные массивы частиц;
- полноэкранная постобработка на игрока;
- обязательные многомегабайтные текстуры.

Обязательно: переиспользование геометрий и материалов, освобождение динамических ресурсов, пул
частиц, ступени качества, LOD по расстоянию, дешёвый вариант для каждого mythic.

### Ступени детализации

| Уровень   | Что происходит                                             |
| --------- | ---------------------------------------------------------- |
| `full`    | всё: аксессуары, вторичное движение, эффекты               |
| `simple`  | аксессуары видны, частицы и дорогие части сокращены        |
| `minimal` | читается силуэт; мелкие визор/голова/спина/след скрываются |

Правило для конкретного предмета:

```js
performance: { simple: 'reduced', minimal: 'hidden' }
```

Умолчания (`simple: 'full'`, `minimal: 'hidden'`) живут в `cosmeticMeta.js`, повторять их у каждой
дешёвой мелочи не нужно. Локальный игрок никогда не получает remote-minimal LOD.

### Бюджет следов

```text
full     до ~12 живых частиц на след
simple   ~6
minimal  ≤3
```

`Digital Ghosts` не клонирует персонажа: это один-два упрощённых силуэта (по одной капсуле) с
низкой частотой появления.

### Мифические

У каждого есть дешёвый вариант, и это проверяется тестом:

- `space-void` — тёмный материал, на full 4 орбитальные частицы, ниже только материал;
- `neon-gl1tch` — редкий сдвиг накладок вместо постобработки, ниже статичный вариант;
- `pirate-abyssal` — океанический материал, минимум частиц, лёгкая волна при приземлении.

### Общие ресурсы

`CosmeticResources.js` кэширует геометрии, материалы и процедурные текстуры на время жизни
страницы. Освобождать их вместе с отдельным персонажем **нельзя**: ими пользуются остальные игроки.
Персонаж освобождает только собственные материалы (у которых своя карта) и свои системы следа,
финиша и эмоций.

## 10. Шкаф

`client/ui/wardrobe.js` + `#wardrobe` в `client/index.html`.

Шкаф не знает ни одного конкретного предмета: всё, что он рисует, приходит из `wardrobeItems()`,
то есть из каталога. Новый предмет появляется в нём сам.

Что есть: превью с вращением пальцем и автоповоротом, вкладки категорий, фильтры (владение,
редкость, коллекция, избранное), карточки с редкостью/коллекцией/требованием/пометкой «новое»,
прогресс коллекций, случайный образ, ячейки эмоций, карточка нового предмета.

**Паритет превью и игры** обеспечен конструкцией: `CosmeticPreview` создаёт тот же `Character` и тот
же `CosmeticRenderer`, что и забег. Отдельной модели или отдельного набора иконок нет — им негде
было бы разойтись.

**Примерка ≠ надевание.** Выбранный предмет подставляется в образ на превью, включая закрытый;
сохранённый loadout меняется только по кнопке «Надеть» и только через обычный server-authoritative
путь.

Избранное и список «уже показанных» предметов хранятся локально и **не являются entitlement**.
Недоступный `localStorage` (приватный режим, переполненная квота) шкаф не ломает: он переходит на
память вкладки.

## 11. Как добавить новый cosmetic

1. Добавить запись в `shared/cosmeticContent.js` (или в унаследованный список, если это правка
   старого предмета).
2. Выбрать существующий `render.kind` и подобрать параметры. Новый kind нужен редко.
3. Указать `unlock` — тип и параметры.
4. Если нужен новый kind: добавить его в `RENDER_KINDS` (`shared/cosmeticValidation.js`) и
   реализовать в `RENDER_KIND_BUILDERS` (`client/game/cosmetics/AccessoryFactory.js`). Тест
   `cosmeticCatalog.test.mjs` проверит, что список и реестр совпадают.
5. Добавить тест, если предмет вводит новое поведение.
6. Всё. Предмет появится в шкафу, в фильтрах, в прогрессе коллекции и в выдаче сервера
   автоматически — вручную править списки не нужно.

Минимальный пример:

```js
{
  id: 'space-comet-tail',
  slot: 'trail',
  name: 'ХВОСТ КОМЕТЫ',
  description: 'Короткий яркий след, который гаснет слишком быстро.',
  rarity: 'epic',
  tags: ['space', 'particles'],
  unlock: { type: 'stat', path: 'race.finishes', gte: 30 },
  render: { kind: 'particle-trail', primary: 0xfff2c4, secondary: 0x6cc6ff, shape: 'star' },
  performance: { simple: 'reduced', minimal: 'hidden' }
}
```

## 13. Чего делать нельзя

- Заводить второй каталог, синхронизируемый вручную.
- Возвращать `switch` по ID предметов в `Character.js`.
- Выдавать entitlement по клиентскому «успеху» — в том числе будущий rewarded/shop/pass.
- Давать косметике влиять на скорость, массу, хитбокс, прыжок, импульс, cooldown, доступ к
  маршрутам или шансы на победу.
- Вешать хитбоксы на аксессуары и делать эмоции боевыми.
- Передавать по сети что-либо, кроме ID и минимальных событий.
- Сбрасывать существующие образы игроков.
